# IR 설계 리서치

> Phase 2 — Research / 주제 1: 모델 간 맥락 전달을 위한 공통 형식(IR, Intermediate Representation)

> ⚠️ **Phase 4 M3 architecture revision 반영 (2026-05-11)** — IR 본 schema는 그대로 유지되나 *refine LLM*과 *inject 흐름*이 변경됨:
> - **Refine LLM**: *활성 모델 헤드리스* (M2 결정) → ***gemini-2.5-flash 헤드리스 강제*** (M3 결정). 사용자 메인 모델 토큰 0 소비. 무료 티어 1000 req/일 활용. 미설치 시 활성 모델 폴백
> - **Inject 채널**: *spawn-time 단일 주입* → ***per-message hook 주입***. claude/codex/gemini 모두 hook system 보유 ([probe 07](../plan/probe_results.md))
> - **Refine 트리거**: handoff 시점 1회 → T-1/T-2/T-3/T-5 + N턴 background compaction. raw turns.jsonl 누적 + N턴마다 background refine
>
> 본 문서 §5(모델별 입력 주입 방식)와 §6(권고 방향)의 *기술적 디테일*은 [02_architecture.md §14](../plan/02_architecture.md) 참조. IR schema(intent/decisions/files/commands/tests/pending/trajectory/artifacts)와 핵심 권고는 그대로 유효.

## 1. 요약

- 현존 표준 중 AgentBridge IR로 그대로 채택할 만한 것은 없다. **MCP**는 도구/리소스 노출용, **A2A**는 에이전트 간 RPC, **AGNTCY/OASF**는 에이전트 메타데이터 스키마로, 모두 "코딩 작업 맥락 전달" 영역과는 다르다.
- **A2A의 데이터 모델**(contextId / Task / Message / Part / Artifact)과 **Claude Code 컴팩션 체크리스트**(intent / files touched / decisions / errors / pending / next steps)가 IR 필수 요소를 가장 잘 정형화하고 있어 핵심 참고 자료.
- 2025–2026년 Amp의 "compaction → handoff" 전환과 OpenAI GPT-5 Codex의 반복 컴팩션 성능 저하 보고는 **재귀 요약(summary-of-summary) 회피, handoff 시점에 fresh 컨텍스트 재구성** 전략을 뒷받침한다.
- AgentBridge MVP IR 권고 방향: **A2A 어휘를 차용한 자체 하이브리드 스키마**(structured 메타데이터 + 압축 trajectory + 원문 보존 영역) + **계층적 압축 + 디스크 오프로딩 + 사용자 검토 단계** 조합.
- 세 CLI 모두 IR 주입은 가능하나 진입 경로가 다르다 — Claude Code(`--system-prompt-file` / `CLAUDE.md`), Codex CLI(stdin + positional prompt), Gemini CLI(`-p` / `GEMINI.md` / stdin) — 어댑터 계층 필요.

## 3. 코딩 에이전트 IR 필수 요소

Claude Code 컴팩션 프롬프트, Amp handoff 동작, A2A 사양, SWE-bench 계열 연구를 종합하면 단순 message 시퀀스로는 표현이 어렵거나 손실되는 정보가 반복적으로 등장한다.

1. **사용자 의도 / 작업 목표 (intent)** — Claude Code 컴팩션의 "User intent and what changed", Amp handoff의 "draft prompt for the next phase". [컴팩션 딥다이브](https://decodeclaude.com/compaction-deep-dive/), [Amp handoff 분석](https://tessl.io/blog/amp-retires-compaction-for-a-cleaner-handoff-in-the-coding-agent-context-race/)
2. **수정/생성된 파일 목록과 diff 또는 현재 상태 스냅샷** — Claude Code는 컴팩션 후 "최근 수정된 5개 파일을 자동 재읽기". 즉 file list는 IR 메타데이터, 내용은 reconstruction 시점에 재취득. [컴팩션 비교 gist](https://gist.github.com/badlogic/cd2ef65b0697c4dbe2d13fbecb0a0a5f)
3. **실행한 명령과 핵심 결과** — Claude Code 마이크로컴팩션은 "오래된 tool output을 디스크로 내보내고 ref만 남김". OpenCode는 "최근 40k 토큰 tool output 보호".
4. **테스트 결과와 실패 내역 (errors encountered and resolutions)** — Claude Code 체크리스트 항목으로 명시. CodeAct는 traceback을 다음 observation의 핵심 입력으로 사용.
5. **미해결 문제 / Pending tasks / Next steps** — Claude Code, Codex CLI 컴팩션, Amp handoff 모두 명시. todo list는 별도 보존 필드 권장.
6. **결정 사항과 근거 (key technical decisions)** — Claude Code 체크리스트의 "Key technical decisions". STITCH(Structured Intent Tracking)는 trajectory의 모든 step에 "Contextual Intent"를 인덱싱한다. [Contextual Intent](https://contextual-intent.github.io/)
7. **A2A 모델로 본 일반 컨테이너** — `contextId`(스레드 ID), `Task`(status/history/artifacts/metadata), `Message`(role+parts), `Part`(text/data/file/url), `Artifact`(산출물). [A2A Core Concepts](https://a2a-protocol.org/latest/topics/key-concepts/)

**구조화 IR이 효과적이라는 사례/벤치마크**

- **SWE-Pruner**: task-aware adaptive context pruning으로 Claude Sonnet 4.5 기준 토큰 23.1%↓, 라운드 18.2%↓, 성공률 +2%p (62→64%). 무차별 압축이 아니라 작업 의도에 맞춘 구조 인지가 효과적임을 시사. [arXiv](https://arxiv.org/html/2601.16746)
- **LLMLingua**: 토큰 단위 압축으로 GSM8K에서 20× 압축에 성능 1.5%p 손실. 단 코드 컨텍스트에서는 "토큰 단위 pruning이 코드 syntax를 깨뜨린다"는 비판이 있음. [arXiv](https://arxiv.org/abs/2310.05736)
- **ContextBench / SWE-ContextBench**: 코딩 에이전트 컨텍스트 검색·재사용 평가용. 1,100여 개 task. [ContextBench](https://arxiv.org/html/2602.05892v1), [SWE-ContextBench](https://arxiv.org/html/2602.08316)
- **MemoryAgentBench / LoCoMo**: 장기 대화 메모리 평가. 35 세션·300+턴 규모. [정리](https://arxiv.org/html/2603.07670v1)

## 4. 토큰 효율 vs 품질 절충 기법

| 기법 | 핵심 아이디어 | 장점 | 단점 | 코딩 적합도 |
|---|---|---|---|---|
| **계층적 요약 (hierarchical summarization)** | 최근 N턴 원문 + 이전은 단계적 요약 (turn → session → topic) | 최근 정확도 유지, 토큰 큰 폭 감소 | "summary-of-summary" 누적 정보 손실. OpenAI GPT-5 Codex 성능 저하 보고됨 | 중 |
| **Semantic compression / LLMLingua** | 토큰 단위 중요도 점수로 prompt 압축 (최대 20×) | task-agnostic, 빠름 | **코드 syntax 파괴 위험** (SWE-Pruner 등이 명시 비판) | 하 |
| **Sliding window + summary memory** | window 밖은 summary로 대체 | 단순, 구현 쉬움 | 윈도우 밖 long-tail 정보(초기 의도/제약) 누락 | 중 |
| **Episodic / vector store retrieval** | 모든 턴 임베딩, 관련 부분만 retrieval | 매우 긴 history도 처리 | 인프라 복잡도↑, retrieval recall 문제, 1인 데스크톱 앱에 과중 | 하 |
| **Microcompaction (tool output 디스크 오프로딩)** | 큰 tool 결과를 파일로 빼고 ref만 유지. Claude Code 채택 | 코드/명령 결과 보존하면서 토큰 절감 | 프롬프트 캐시 hit 유지에 prefix 안정성 필요 | **상** |
| **Task-aware structured pruning (SWE-Pruner)** | 현재 task 의도에 맞춰 trajectory를 선택적으로 잘라냄 | 토큰 23%↓ + 성공률 +2%p | 구현 난이도, 추가 LLM 콜 비용 | **상** |
| **Amp handoff (요약 대신 새 thread + 선별 carry-forward)** | 다음 단계 prompt를 LLM이 초안 → 사용자 검토 → 선별 파일·아티팩트만 새 thread로 | 재귀 요약 회피, 사용자 통제, 모델 전환에 본질 적합 | 원문 trajectory의 일부 nuance 손실 | **상** |

**공개된 정량 수치**

- LLMLingua: 20× 압축, GSM8K -1.5%p. [arXiv](https://arxiv.org/abs/2310.05736)
- LongLLMLingua: 4× 압축, +17.1%p (long-context). [arXiv](https://arxiv.org/html/2310.06839v2)
- SWE-Pruner: 23.1% 토큰↓, 18.2% 라운드↓, +2%p 성공률 (Claude Sonnet 4.5). [arXiv](https://arxiv.org/html/2601.16746)
- Claude Code 컴팩션 트리거: `effective_context - 13,000` 토큰. 컴팩션 후 최근 5개 파일 재읽기(파일당 ≤5,000 토큰, 총 ≤50,000 토큰). [딥다이브](https://decodeclaude.com/compaction-deep-dive/), [gist](https://gist.github.com/badlogic/cd2ef65b0697c4dbe2d13fbecb0a0a5f)

## 5. 모델별 입력 주입 방식

### Claude Code

- **세션 저장**: `~/.claude/projects/<encoded-path>/<uuid>.jsonl`. 라인당 JSON(type=user|assistant, message, gitBranch, cwd 등). [Sessions](https://code.claude.com/docs/en/sessions)
- **재개**: `claude --continue` (마지막), `claude --resume <session-id>`.
- **Export**: `/export` (clipboard 또는 plain text 파일).
- **IR 주입 옵션**:
  - `--system-prompt "<text>"` 또는 `--system-prompt-file <path>` (상호 배타).
  - `--append-system-prompt`.
  - `CLAUDE.md`는 default system prompt에 자동 주입 → AgentBridge가 임시 `CLAUDE.md`를 만들거나 `--system-prompt-file`로 주입.
  - 첫 user 메시지에 IR prepend도 가능.
  - 출처: [CLI 레퍼런스](https://code.claude.com/docs/en/cli-reference), [system prompt 수정](https://platform.claude.com/docs/en/agent-sdk/modifying-system-prompts)

### Codex CLI

- **세션 저장**: `~/.codex/sessions/YYYY/MM/DD/rollout-<timestamp>-<id>.jsonl`. [레퍼런스](https://developers.openai.com/codex/cli/reference)
- **재개**: `codex exec --experimental_resume=<path-to-jsonl>`. interactive mode에는 picker. [Discussion #1076](https://github.com/openai/codex/discussions/1076)
- **IR 주입 옵션**:
  - Positional argument: `codex exec "<prompt>"`.
  - Stdin 단독: `codex exec -` (stdin 전체가 prompt).
  - **Prompt + Stdin**: `echo "<IR>" | codex exec "<instruction>"` → stdin이 `<stdin>` 블록으로 prompt 뒤에 append. AgentBridge가 IR을 stdin으로 주입하기에 적합.
  - 출처: [Non-interactive](https://developers.openai.com/codex/noninteractive), [stdin 패턴](https://codex.danielvaughan.com/2026/04/15/codex-exec-unix-pipelines-prompt-plus-stdin/)

### Gemini CLI

- **세션 저장**: `~/.gemini/tmp/<project_hash>/chats/`. 백그라운드 자동 저장. [Sessions](https://geminicli.com/docs/cli/session-management/)
- **재개**: `gemini --resume` (최근), `gemini --resume <index|UUID>`.
- **Export**: `/chat share <file>.md` 또는 `<file>.json`. JSON export 공식 지원. [Issue #26029](https://github.com/google-gemini/gemini-cli/issues/26029)
- **IR 주입 옵션**:
  - `gemini -p "<prompt>"` (non-interactive).
  - `gemini -i "<prompt>"` (interactive 시작 prompt).
  - Stdin: `echo "<text>" | gemini`.
  - `GEMINI.md`(홈 또는 워크스페이스 계층) 자동 concat. `GEMINI_SYSTEM_MD` 환경변수로 system prompt override.
  - 출처: [GEMINI.md](https://geminicli.com/docs/cli/gemini-md/), [System Prompt Override](https://geminicli.com/docs/cli/system-prompt/), [Commands](https://geminicli.com/docs/reference/commands/)

**공통 관찰**: 세 CLI 모두 (1) JSONL/JSON 자동 세션 저장, (2) `--resume` 또는 유사 플래그, (3) markdown 또는 plain text export, (4) system-prompt 또는 첫 user 메시지로 IR 주입을 지원한다. AgentBridge는 각 CLI export를 IR로 정규화하여 저장하고, 다른 CLI 호출 시 system-prompt-file 또는 stdin으로 주입하는 어댑터 패턴이 자연스럽다.

## 6. 권고 방향

### 6-1. 기존 표준 채택 vs 자체 설계

**자체 설계 + A2A 데이터 모델 차용**.

- 어떤 표준도 "코딩 에이전트 간 작업 맥락 전달"을 직접 다루지 않는다. MCP/AGNTCY는 영역이 다르고, A2A는 전송 프로토콜과 묶여 있어 그대로 쓸 수 없다. OpenAI Threads/LangGraph state는 너무 일반적.
- 단, A2A의 `contextId` / `Task` / `Message` / `Part` / `Artifact` 어휘는 그대로 차용. 외부 호환성 확보 + 표준 정렬된 시그니처는 향후 다른 에이전트와의 통합 마이그레이션 비용을 낮춘다.

### 6-2. 구조화 스키마 vs 메시지 시퀀스 vs 하이브리드

**하이브리드** (structured envelope + 압축 message trajectory + 원문 보존 영역).

권고 IR 스켈레톤(개념적):

- `contextId` — UUID, 스레드 ID
- `meta` — { 작성 시각, 생성한 모델/CLI, 워크스페이스 경로, git 브랜치/HEAD }
- `intent` — { goal, role: design|implement|review|..., constraints[] }
- `decisions` — [{ topic, choice, rationale, ts }]
- `files` — [{ path, status: modified|created|deleted, lastReadAt, summary }] (내용은 ref + 짧은 요약)
- `commands` — [{ cmd, exitCode, summary, fullOutputRef? }]
- `tests` — [{ name, status, failureSummary }]
- `pending` — [{ task, blockers, nextStep }]
- `trajectory` — [{ role, content_compressed, originalRef? }] (최근 N턴은 원문 보존, 그 이전은 요약)
- `artifacts` — [{ id, name, mediaType, ref }]

이 스키마는:

- 단순 message[]보다 코딩 작업의 핵심(intent/decisions/files/commands/tests/pending)을 명시 필드로 보존 — SWE-Pruner·STITCH·Claude Code 컴팩션 체크리스트가 일관되게 가리키는 정보 카테고리.
- 순수 structured보다 trajectory를 함께 두어 "왜 그렇게 결정했는가"의 자연어 맥락도 유지.
- 큰 객체(파일 내용, 명령 출력 전문)는 disk ref로 외부화 — Claude Code 마이크로컴팩션 패턴.

### 6-3. 토큰 압축 전략

**계층적 + 디스크 오프로딩 + Amp식 handoff 시점 압축**.

1. **저장 시점**: trajectory 원문 100% 저장 (파일이므로 토큰 비용 무관).
2. **모델 전환 시점(=handoff)**: 다음 모델에 주입할 IR을 LLM이 한 번 정제.
   - 최근 K턴(예: 10턴) 원문 유지.
   - 그 이전은 structured 필드(decisions/files/commands/pending)로 추출 + 자연어 요약 1~2문단.
   - 큰 tool output은 ref만 두고 필요 시 새 모델이 도구로 재취득.
3. **재귀 압축 회피**: handoff 시점마다 원본 trajectory에서 다시 정제. 요약의 요약은 만들지 않는다.
4. **사용자 검토 단계**: Amp 패턴처럼 IR 초안을 사용자에게 보여주고 carry-forward 항목을 토글 가능하게. 1인 데스크톱 앱이라는 특성상 가능.

LLMLingua류 토큰 단위 압축은 코드/명령/diff에 적용 금지(syntax 파괴). 자연어 trajectory에만 옵션으로 제공.

## 7. 미해결 질문 (Plan 단계 의사결정)

1. **IR 직렬화 포맷** — JSON vs JSONL vs YAML vs MessagePack. 사람 가독성 vs 머신 효율.
2. **trajectory 보존 깊이** — 최근 K턴의 K를 고정값(예: 10) vs 토큰 예산 기반 동적. 모델별 컨텍스트 윈도우 차이 고려.
3. **요약 생성 모델 선택** — handoff 정제용 LLM을 어디서 호출할지(현재 활성 모델? 별도 작은 모델? 사용자 선택?). 비용/품질/지연 trade-off.
4. **파일 ref 처리** — AgentBridge가 파일 스냅샷을 자체 저장할지(git이면 commit hash로 충분?) vs 매번 디스크에서 재읽기. 파일 변경 상태에서 과거 IR을 다른 모델에 줄 때의 일관성 문제.
5. **A2A 어휘 차용 범위** — Task/Message/Part/Artifact만 가져갈지, AgentCard·streaming·extension까지 흉내낼지. 후자는 MVP 과잉.
6. **CLI별 어댑터 위치** — 각 CLI 세션 파일을 직접 읽는 importer + IR을 system-prompt/stdin으로 주는 exporter 추상화. CLI 업데이트로 포맷이 깨질 위험에 대한 fallback.
7. **모델 전환 시 사용자 가시성** — handoff 직전 IR을 사용자가 편집할지(Amp 패턴), 아니면 자동? MVP 단순성 vs 사용자 통제.
8. **Claude Code의 `CLAUDE.md` 충돌** — 임시 CLAUDE.md 작성 시 사용자 기존 CLAUDE.md와 충돌. `--system-prompt-file`이 안전하나 CLI 옵션 향후 변경 위험 — 확인 필요.
9. **민감 정보 처리** — trajectory에 API key·내부 코드·비밀번호 노출 가능. IR 생성 시 redaction 정책 — 별도 연구 필요.
10. **IR 품질 검증 방법** — ContextBench/SWE-ContextBench가 있으나 1인 개발 환경에서 실행 가능한지 — 확인 필요.
